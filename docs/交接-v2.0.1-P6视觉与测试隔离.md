## 一、本批交付了什么

### 1. 文献图片「AI 识别」（视觉标注）
- `POST /api/library/figures/{fig_id}/caption`：单图识别 → 写回图注，来源标记 `vision`；
  未启用视觉 → **409**（中文说明去哪个开关）；图不存在 → 404；模型报错 → 200 + `ok:false` + 原因。
- `POST /api/library/papers/{paper_id}/figures/caption`：批量；默认跳过已有 `vision|user`，
  `force=true` 重做；按页序、`limit` 默认 10（上限 50，控费）；单张失败不影响其余。
- 前端「文献图片」面板：单张/批量「AI 识别」按钮 + 「视觉标注/原文/人工」徽标；
  **仅当设置页启用视觉读图后才显示按钮**（不显示灰按钮误导）。
- 流水线 `src/literature/figure_caption.py`：端点与助手工具共用同一实现。
  **双写**：`figures_index.json`（事实来源）+ `library.db` 镜像 —— 只写 DB 会被
  `POST /api/library/rebuild` 冲掉，这是本批最容易踩的坑。

### 2. 助手直接看图
- 新工具 `view_figure`（`list` 列图 / `read` 视觉读图 / `save_caption` 写回标注），
  已注册进 `registry.TOOLS`（含中文 schema 说明与费用提示）。
- 视觉未启用/调用失败 → 返回 `ok:false` + 中文原因 + 可操作建议，**绝不编造图中内容**。

### 3. 助手截图提问（仅桌面版）
- `desktopCapturer` 截主屏 → 自动进附件；PNG 超约 4MB 自动降级 JPEG(85)。
- 真机自检：`2048×1152@1.25 → 2560×1440`、非空、PNG 0.40MB、`RESULT=OK`。

### 4. 带图轮次自动切视觉模型
- `chat_completion_with_tools` 检测到 `image_url` 分片 → 本轮用「视觉读图」配置的
  模型/端点/Key；未配置/读坏了则沿用对话模型（不因配置问题挂掉对话）。

### 5. PDF 自适应跟随容器 + 删批注连带删图（两个遗留小尾巴）
- 前端：拖侧栏/缩放窗口后重算自适应（120ms 防抖、手动缩放不覆盖、点百分比恢复自适应）
  —— **已热更新到你的安装版**。
- 后端：删批注时清理 `literature/annotations/**` 内截图（越权路径拒绝、删不掉只记日志）。

## 四、必须知道的坑与折扣（不粉饰）

1. **前端未热更新**：新按钮依赖本批**后端**端点，安装版后端还没有 → 热更新只会让按钮
   404。本批 UI 必须等下次打包。
2. **端点前缀不统一**：新标注端点在 `/api/library/...`（文献库路由），列图仍在
   `/api/literature/...` → 前端有两个 BASE。功能无影响，要统一需搬端点或加别名。
3. **批量进度只有「已耗时 + 转圈」**：批量端点是单次 HTTP（无 SSE），期间按钮 disabled、不可取消。
4. **`view_figure` 的二次确认只在 `save_caption=true` 时弹**：只读看图不弹（单图 ≤1024 token，
   费用极低），但会调云端模型；若你希望"任何读图都确认"，改 `confirm_impact` 一行。
5. **尚无真实云端视觉调用**：所有视觉调用在测试里打桩/走假端点。真机首图请你自己点一次
   「AI 识别」确认（DeepSeek 端点的 Key 我没有、也不该替你花）。
6. **`paper_id` 不存在时批量端点返回 200 + requested=0**（未做 404）。
7. **数值可靠性**：官方图片会缩放到约 1300×1300 等效 → 密集谱图的精确数值仍建议人工复核，
   提示词已强制"读不准宁可不写"并要求 `confidence`。

## 五、测试隔离事故与修复（重要，务必保留）

**事故**：`tests/test_literature_autobackfill_v197.py` 等用例会写**真实**数据目录。
根因：`literature.resolver.INTAKE_PATH`、`figures.FIGURES_DIR/INDEX_PATH`、
`pdf_figures.STAGING_DIR`、`knowledge.ENTRIES_PATH`、`attachments.PDFS_DIR/INDEX_PATH`、
`embedding.EMB_PATH` 都是**导入期常量**，而 `tests/conftest.py` 的会话夹具在
collection **之后**才执行 → 常量仍指向仓库真实数据目录。

**后果（已量化）**：仓库 `data/literature/literature_intake.jsonl` 累积 **335 行测试垃圾**
（9/12–今天，全部是 `10.1000/*` 与 "New COF Paper"），dev 镜像库 `paper 1` / `paper 2`
的标题被占位文献**覆盖**。（`data/paper_titles.json` 未受影响，1711 条完好；
`data/literature/**` **不在打包清单**，所以 v2.0.0 安装包没被污染。）

**修复**：
- `tests/conftest.py::_refresh_module_level_paths()` 扩容：把上述 7 个模块的写盘常量
  连同原有 gnn 两处一起重算到会话隔离目录；
- 新增 `tests/test_test_isolation_redline.py`：**红线测试**，任何写盘常量若仍指向
  `data/` 就直接失败（含随包库只读检查）；
- `tests/test_literature_overlay.py` 的原断言其实在断言"泄漏后的默认值"，改为
  显式按无 `COF_DATA_DIR` 环境重算后再比对（并在 finally 里先恢复环境再重算，
  避免把真实路径留在内存里）。

**清理与备份**：intake 已清空（335 → 0），镜像库已 `rebuild` 重建
（1711 条、0 污染、paper 1/2 标题与随包库逐字一致）。
备份在 `E:\cof-build\dev-data-backup-20260922-173521\`（含原 intake 与旧 library.db）。
**实测**：跑完整场 1286 个用例后，`intake` 仍为 0 行、`paper_titles.json` 与
`knowledge_entries.jsonl` 指纹不变。

> 教训：**"测试不写真实数据"必须由可执行断言守住**，不能靠注释和自觉 —— 这已是第二次
> 同类事故（第一次是 3 篇测试文献差点冻进 v1.9.8 安装包）。
