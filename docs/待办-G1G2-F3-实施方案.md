## 一、G1 + G2：一个「文献图谱工具」同时覆盖两项

**目标**
- G1：助手回答时能读**文献引用/相似/实体图**（cites / similar_to / technique·metric·property），
  与内置反应图**并存**，并在回答里标注来源。
- G2：把图查询 DSL（neighbors / path / by_entity / by_metric / cites_of / top）作为**助手工具**。

**做法（一个工具即可覆盖，不必拆两个）**

1. 新建 `src/assistant/tools/litgraph.py`：
   ```python
   def lit_graph_tool(mode: str, **kw) -> dict:
       """mode ∈ {neighbors, path, by_entity, by_metric, cites_of, top, analytics}"""
       # 复用已完成的模块（都已在 v1.9.8 落地并有测试）
       from literature import graph_query        # execute(conn, "neighbors 1529 depth=1")
       from literature import graph_analytics    # pagerank / communities / bridges / timeline
       from literature import library_db         # connect()
       conn = library_db.connect(); library_db.ensure_ready()
       if mode == "analytics":
           kind = kw.get("kind", "pagerank")
           return getattr(graph_analytics, kind)(conn) if kind != "timeline" else graph_analytics.timeline(conn)
       dsl = kw.get("dsl") or _build_dsl(mode, kw)   # 把结构化参数拼成 DSL 文本
       return graph_query.execute(conn, dsl)
   ```
   - 返回结构里**保留 `op` 与命中来源**（`graph_query.execute` 已带 `op`；引用边带 `source=crossref`、
     相似边带 `source=embedding`）→ 助手可据此标注「确证引用 / 算法推荐」。
   - **只读**：`graph_query` 已是白名单 + 只读（`drop table items` 会被拒），无需额外防护。

2. 注册（`src/assistant/registry.py`）：
   - 在 import 区（第 20 行附近，与 `from .tools.graphrag import query_graphrag_tool` 并列）加
     `from .tools.litgraph import lit_graph_tool`
   - 在 `TOOLS` 字典里加一项（形状照抄相邻条目：`"name": {"fn": ..., "schema": {...}}`；
     `schema` 用 OpenAI tools 格式，参数含 `mode` 枚举 + 可选 `dsl`/`paper_id`/`name`/`min`/`max`/`limit`）
   - `describe_tools()` 会自动带上（路径 B 的文本提示）；`_available_tools()` 的裁剪逻辑无需改。

3. 助手提示词（可选但推荐）：在 `src/assistant/persona.py` 的工具说明里加一句
   「需要**文献之间**的关系（谁引用谁、相似、谁用了某技术/指标）时用 `lit_graph`；
   需要**化学反应网络**（单体/溶剂/催化剂/成膜结果）时仍用 `query_graphrag`」——
   明确两套图的边界，避免模型混用。

4. 测试：新建 `tests/test_assistant_litgraph.py`（照 `tests/test_graph_query_v198.py` 的 fixture 写法）：
   - `mode=neighbors` 返回邻域；`mode=by_metric` 命中数值（中文同义词表已就绪）
   - `mode=top` 返回排行；`mode=path` 返回路径或「未找到」
   - 非法 mode / 非法 DSL → 明确报错而不是抛栈
   - 断言工具已注册：`registry` 的 schema 列表里含 `lit_graph`

**验收**：在助手问「和 1529 怎么联系上的」「谁用了 PXRD 且比表面积>2000」「被引最多的是哪几篇」，
助手应调用该工具并给出**带来源标注**的答案。

## 二、F3：方案库（用户最早提出，至今未做）

**三个子项**

1. **删除能力**
   - 后端：`api/routers/iterate.py` 增 `DELETE /api/iterate/plans/{plan_id}`
     （plan 存储见该路由内的 plan 读写函数；删除后返回 `{ok, plan_id}`，未找到返回 404）
   - 前端：`webapp/src/components/mine/PlansSection.tsx` 每张卡加**删除按钮**
     （二次确认 → 调删除接口 → 从本地列表移除 → toast）

2. **方案卡接 LLM 并按"讨论确定的用量"生成**
   - 现状：`src/recommend/plan_card.py` 是**纯模板**（无 LLM、无用量）；
     真实用量只在 `generated_plans.py` 的 `adjustments_applied`，且从未回填 `conditions`。
   - 改法：新增 `src/recommend/plan_card_llm.py`
     - 输入：单体对（SMILES/名称）、目标（如"高结晶度薄膜"）、**用户与助手讨论确定的用量**
       （醛/胺摩尔比、溶剂、催化剂当量、温度/时间）、可选文献证据（来自 `entry_metrics`/结构化条目）
     - 输出：**结构化 JSON**（步骤 + 每步用量 + 依据），用 JSON Schema 校验 + 局部重试
       （复用 `src/literature/reading_llm.py` 的 `_chat` 与校验思路）
     - 落库：写入方案卡时**把用量写入 `conditions`**（修复"方案卡没有用量"的根本问题）
   - 前端：方案卡生成入口改为「与助手讨论确定用量 → 生成」，或至少在卡片上**显示用量来源**
     （讨论得出 / 默认建议）

3. **助手加入方案卡工具**
   - 新建 `src/assistant/tools/plan_manage.py`：`create_plan_card` / `update_plan_card` /
     `delete_plan_card`（走同一存储层），并在 `registry.py` 注册（同 §一.2 的写法）
   - 提示词里说明：「生成方案卡前**必须先与用户确认用量**」——对应用户的第 3 条决策

**验收**：方案库卡片有删除键；新生成的方案卡**带具体用量**且能说明依据；助手能创建/修改/删除方案卡。
