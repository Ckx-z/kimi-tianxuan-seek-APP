## 问题 1：深度研究引用跳转错误

- **原因分析**：
  1. 生成侧：`src/assistant/research.py::_WRITER_PROMPT`（L97-99）要求参考文献格式为
     `` `[n] 标题. 期刊, 年份. DOI: 10.xxxx/...（https://doi.org/...）` ``，
     URL 被**全角括号**包裹且不是 markdown 链接语法。
  2. 渲染侧：`react-markdown` + `remark-gfm` 的 autolink literal 只修剪 ASCII 尾随标点
     （`)` `.` `,`），**不识别全角 `）`** → `href="https://doi.org/…）"`。
  3. 打开侧：正文气泡 `MessageBubble.tsx` 的 `a` 组件有 `openExternal` 兜底（L80-98），
     但「会话综合报告」弹窗（`Assistant.tsx` L1163）用**裸 `ReactMarkdown`、无 components 映射**，
     Electron 内会就地导航 → 白屏/错误页。
  4. 另有一类合法但脆弱的 URL：`chem.libretexts.org/..._Websites_(Inorganic_Chemistry)/...`
     （含成对括号），autolink 修剪策略会导致括号被误删或误留。
- **修复方案**：
  1. 生成侧改模板（首选）：要求 LLM 输出**标准 markdown 链接**并禁止尾部全角括号：
     `[n] 标题. 期刊, 年份. DOI: [10.xxxx/...](https://doi.org/10.xxxx/...)`，
     并在 prompt 明确「URL 必须是 `[文本](URL)` 形式，URL 内不得含中文标点」。
  2. 渲染侧兜底（必做，兼容历史报告）：新增 `normalizeRefLinks(md)`：
     - 修剪链接目标尾部 `）)】]，,。.；;、` 等（含全角）；
     - 把正文里裸 URL 后的全角括号移出链接；
     - 报告渲染统一走一套 `mdComponents`（把 `MessageBubble.mdComponents` 提到公共模块复用），
       弹窗也不再内联导航（`target=_blank` + `openExternal`）。
  3. 兜底数据源：报告的 `refs` 数组本身干净，可在「参考文献」区下方渲染结构化引用列表
     （点击用 `refs[].url`），保证即使正文有脏 URL 也能正确跳转。
  4. 加单测：给定含 `）`、成对括号 URL、裸 URL 的历史 markdown → 归一化后 href 全部合法。
- **涉及文件**：
  - `src/assistant/research.py`（`_WRITER_PROMPT` L92-102；`_session_report` 提示词同理）
  - `webapp/src/lib/markdown.ts`（新建：`mdComponents` + `normalizeRefLinks`）
  - `webapp/src/components/assistant/MessageBubble.tsx`（改为引用公共渲染器）
  - `webapp/src/pages/Assistant.tsx`（L1163 综合报告渲染；报告详情弹窗）
  - `tests/test_research_refs.py`（新建）

## 问题 2：知识库补解析多文件上传（主文 + SI）

- **原因分析**：
  1. 前端单文件：`LiteratureKnowledgeSection.tsx` L592-601 `type="file"` **无 `multiple`**，
     且只取 `e.target.files?.[0]`。
  2. 后端单文件：`api/routers/literature.py::parse_paper`（L340-366）签名为
     `file: UploadFile | None`，且**只跑 `fitz` 逐页 `get_text()` 后立即丢弃字节**。
  3. **没有任何文献附件存储**：`data/literature/` 只有 `knowledge_entries.jsonl`（+ figures 索引/图片），
     上传的 PDF 不留存 → 无法「同一文献多附件」、无法复用、无法回看。
  4. 追加缺陷：`parse_paper` **没有文件大小上限**（对比 `extract_pdf` 有 20MB 校验），
     也没有「无文本层」检测（空白文本只报「请提供 PDF 文件或 text 全文」，误导性强）。
- **修复方案**：
  1. 新增附件层 `src/literature/attachments.py`（照 `figures.py` 的索引 + 原子写模式）：
     - 存储：`user_data_root()/literature/pdfs/<paper_id>/<sha1[:12]>_<safe_name>.pdf`
       （内容 hash 去重，同文件重复上传不重复占盘）；
     - 索引：`user_data_root()/literature/pdfs_index.jsonl`，字段
       `{file_id, paper_id, filename, role: main|si, size, sha1, uploaded_at, pages, chars}`；
     - 约束：单文件 ≤20MB、仅 `.pdf`、单文献 ≤8 个附件。
  2. 路由：
     - `POST /api/literature/{paper_id}/attachments`（`files: list[UploadFile]` + `role` Form）
       → 批量上传、返回元信息；
     - `GET /api/literature/{paper_id}/attachments`（列表）、`GET .../attachments/{file_id}/file`（下载/预览）、
       `DELETE .../attachments/{file_id}`；
     - `POST /{paper_id}/parse` 改为 `files: list[UploadFile] | None` + `use_stored: bool = False`：
       主文在前、SI 依次追加，每条前插分隔标记 `\n\n=== [SI 1] <filename> ===\n`，
       合并后交给 `llm_extract.parse_text`（分段逻辑已能处理超长）；返回值新增
       `sources: [{filename, role, chars}]` 供前端展示「本次解析包含哪几个文件」。
  3. 前端：
     - 文件 input 加 `multiple`，允许「主文 1 份 + SI 多份」，上传后展示附件 chips（角色可切换 主文/SI、可删除）；
     - 新增「用已存附件解析」按钮（`use_stored=true`），避免每次重传大文件；
     - 文献卡片新增附件列表（文件名/大小/页数/解析状态），解析预览标注来源文件。
  4. 解析语义：主文与 SI **合并提取但要区分来源**——条目 `evidence` 前缀 `[SI1]`，便于核对；
     入库后条目仍按 `group_id` 归组。
- **涉及文件**：
  - `src/literature/attachments.py`（新建）、`src/literature/__init__.py`
  - `api/routers/literature.py`（`parse_paper` L340-366 + 新附件端点 + 大小/文本层校验）
  - `api/schemas.py`（附件元信息模型）
  - `webapp/src/components/mine/LiteratureKnowledgeSection.tsx`（L194-215 `runParse`、L584-623 弹窗）
  - `webapp/src/components/mine/api.ts`（附件 API）
  - `tests/test_literature_attachments.py`（新建）

## 问题 3：LLM 结构化提取失败

- **失败原因分析（是否需视觉模型）**：
  1. **主因（已实测复现，E3/E4）**：文献解析 LLM 配的是 `deepseek-v4-flash`（**推理模型**），
     `src/literature/llm_extract.py::_chat` 硬编码 `max_tokens=4000`。
     实测：4000 token 全部消耗在 `reasoning_content`（`reasoning_tokens=4000`），
     `finish_reason=length`、`content` 空 → `_parse_json_array("")` 返回 None →
     重试同预算仍空 → `all_entries` 为空 → 降级 `_scan_smiles_candidates` → 条目为 0（或仅几条无标签候选）。
     **这就是「提取失败/不完整」的直接原因**（升到 16000 立刻产出 2 条合法条目）。
  2. **次因 A**：prompt 未覆盖**文献级元数据**（title / authors / journal / year / doi / abstract）。
     老文献这些字段来自 Crossref；新文献若走 LLM 提取，不会补上 → 与用户期望「和老文献一样」不符。
  3. **次因 B**：分段策略 `MAX_TEXT_CHARS=24000` 无重叠、`group_id` 按段独立生成（多段都出现 `E1`），
     跨段同号不同组易混淆；`defensive` 去重键含 evidence 前 80 字才侥幸不误删。
  4. **次因 C**：`_chat` 超时 180s/段，实测每段 ~38s；190k 字符主文 = 8 段 ≈ 5 分钟，
     前端 `req()` 无超时（不会中断）但**无进度反馈**，用户易误判为卡死/失败。
  5. **次因 D**：`parse_paper` 对扫描件无检测、无 OCR、无 Vision，
     空白文本只回「请提供 PDF 文件或 text 全文」。
  6. **视觉模型可行性评估**：本机语料 156/156 为文本型 PDF（E6）→ **当前不需要 OCR/Vision**。
     若未来遇到扫描件/图表/光谱图，按性价比排序：
     - 方案 A（0 新依赖，推荐先做）：文本层检测 + 明确提示 + `page.get_text()` 已含表格文本；
     - 方案 B（离线 OCR）：`rapidocr-onnxruntime`（CPU、约 50–80MB，py3.8 需锁 `onnxruntime<=1.16`），
       每页 1–3s，打包体积 +~80MB；
     - 方案 C（Vision LLM）：当前 `deepseek-v4-flash` **无视觉能力**，需另配 Qwen-VL / GPT-4o 类端点，
       每页约 1–2k tokens（12 页 ≈ 2 万 tokens/篇），适合 SI 图表/光谱；
       建议做成**可选开关**（仅当用户配置 vision 模型时启用），不作为默认路径。
- **修复方案**：
  1. `_chat` 改为**按模型类型分配预算**：`max_tokens` 默认 16000，可配置；
     检测到「content 为空但 reasoning 非空 / finish_reason=length」时**自动翻倍重试**（上限 32000），
     并把该情形写入返回 note（前端可见「推理模型预算不足已自动扩容」）。
  2. 拆分两步提取：
     - Step 1（首段）额外提取 `paper_meta`（title/authors/journal/year/doi/abstract），
       经用户确认后**只补空字段**回写文献库（新端点 `PATCH /api/literature/papers/{paper_id}`，
       永不覆盖已有值；DOI 命中重复时提示）；
     - Step 2 逐段提取条目（现有逻辑），段间 group_id 加段前缀（`E1` → `C2-E1`）防撞。
  3. 解析进度与健壮性：
     - 新增 `POST /{paper_id}/parse-job`（异步 job + `progress.jsonl` 轮询，复用 GNN 重训 job 模式），
       前端显示「第 i/N 段 · 已提取 M 条」；同步接口保留用于小文本/兼容；
  4. 文本层检测：`chars/page < 50` 时返回 422 + 明确文案（「疑似扫描件，当前版本不解析图片型 PDF」），
     并在 note 里建议 OCR/Vision 方案（后续版本按需接入）。
  5. 前端「结构化条目」区域：解析完成即展示分组预览（现有），
     `paper_meta` 单独一栏「文献信息（可回填）」。
- **编号递增方案**：
  - 现状**已正确**（E8：内置库最大 id 1781 → `next_paper_id()` 返回 `1782`；`append_paper` 写用户库
    `data/literature/paper_titles.json` 后 `titles.reload()`，连续新增会 1782、1783…）。
  - 需要做的只是**可见性与防回归**：
    1. 录入确认页与知识库卡片显示「文献编号 #1782（全库第 1712 篇）」；
    2. 加测试 `test_next_paper_id_after_1781`（造内置库最大 1781 → 断言 1782、再 append 断言 1783）；
    3. `next_paper_id()` 增加防御：忽略非数字 key（已有）+ 跳过已存在 id 冲突（新增断言，防并发写）。
- **涉及文件**：
  - `src/literature/llm_extract.py`（`_chat` L142-162、`_PROMPT`、`parse_text` L218-264、分段/预算逻辑）
  - `src/literature/resolver.py`（`next_paper_id` L131-134、`append_paper`）
  - `api/routers/literature.py`（`parse_paper`、新增 `PATCH /papers/{id}`、`parse-job`）
  - `api/schemas.py`（paper_meta 模型）
  - `webapp/src/components/mine/LiteratureKnowledgeSection.tsx`（解析进度、文献信息栏）
  - `webapp/src/components/settings/LiteratureLlmSettingsCard.tsx`（可选：max_tokens / vision 开关）
  - `tests/test_literature_knowledge.py`、`tests/test_literature.py`（编号与提取回归）

## 问题 4：科研助手精修

### 4.1 助手读不到实验过程时间线（完整实验流程）

- **原因分析**：
  1. `src/assistant/tools/records.py::_fmt_record`（L22-55）**完全没有输出 `process_notes`**（完整实验流程长文本）；
  2. timeline 只输出**最后 5 条**（`_MAX_TIMELINE=5`）且每条截断 120 字（`_cut(..., 120)`），
     而本机 36 条记录里 6 条 timeline > 5 条（E7，最长 12 条）；
  3. 单次最多 10 条记录（`_MAX_RECORDS=10`），且没有按 `record_id` 取单条全量的工具；
  4. `src/assistant/context.py::_records_block`（L111-140）注入的摘要同样只有 record_id/date/outcome +
     自我总结/失误摘要，**没有流程与时间线**；
  5. 时间线附件只存元信息，工具输出里未列出。
- **修复方案**：
  1. `_fmt_record` 补齐：`process_notes`（截断 1200 字并标注「已截断，需要全文请调 read_experiment_record」）、
     **全部 timeline 条目**（不再只取尾部，按总字数 4000 截断，且**必保第一条时间点**）、
     附件文件名列表、`experiment_date`。
  2. 新增只读工具 `read_experiment_record(record_id, include_timeline=True)`：
     返回单条全量（`process_notes` 全文 ≤4000 字、每条 timeline ≤600 字、附件清单），
     注册进 `src/assistant/registry.py`，并加入 `research.py::available_research_tools` 白名单。
  3. `context.py::_records_block`：锚定收藏时，对最近 1 条补 `process_notes`（≤600 字）+ 首末时间点。
  4. 新增测试：12 条 timeline 的记录 → 工具输出包含全部 12 个 `time_label` 与 process_notes 前 1200 字。
- **涉及文件**：`src/assistant/tools/records.py`、`src/assistant/registry.py`、`src/assistant/context.py`、

## 问题 5：实验记录时间应取时间线第一个时间点

- **原因分析**：
  1. `src/records/store.py::create_record` L279 `"date": _today()` —— `date` 语义是**录入日期**，
     与实验起始时间无关；
  2. timeline 的 `time_label` 是**自由文本**（本机实测格式混杂）：
     `2026-9-10 8:59`、`2026-8-19  11:39`（双空格）、`26/7/3/10:30`、`26/7/6/10:30`，
     还有笔误 `2026-8-123 11:39` —— 解析必须容错；
  3. 消费方全部直接用 `date`：前端 `Home.tsx`(L75/168)、`Records.tsx`/`RecordTimeline.tsx`(L193)、
     `RecordDetailDialog.tsx`(L106)、`RecordEditDialog.tsx`(L156-157)、`FavoritesSection.tsx`(L766)、
     `Iterate.tsx`(L37)；Python `assistant/tools/records.py`、`assistant/context.py`(L134)、
     `assistant/brief.py`(L237/501/513)、`records/export_docx.py`(L401)、`records/store.py::list_records` 排序(L325)；
  4. 实测影响：36 条记录中普遍存在 1–24 天偏差（如 `rec_20260912_002`：date=2026-09-12，实际起始 2026-09-10）。
- **修复方案**：
  1. 新增 `src/records/dates.py`：
     - `first_time_point(timeline) -> (iso_date|None, raw_label|None, confidence)`：
       逐条尝试 `YYYY-M-D[ H:MM]`、`YYYY/M/D`、`YY/M/D[/H:MM]`（`26/7/3/10:30` → 2026-07-03）、
       `D/M/YYYY`、`M/D/YYYY`、`第N天`（相对创建日推算，置信度 low）；
       **非法值跳过继续**（`2026-8-123` → 跳过），返回首个合法值；
     - 空 timeline / 全部不可解析 → `(None, None)`。
  2. `store._normalize_record` 增加**派生只读字段**（不覆盖 `date` 语义）：
     `experiment_date`（= 首个时间点 or `date`）、`date_source`（`"timeline"` / `"created"`）、
     `date_label`（原始标签）；`list_records` 排序改为 `(experiment_date, record_id)`（并保留旧排序兜底）。
  3. 前端统一取 `rec.experiment_date ?? rec.date`；`date_source == "created"` 时显示
     「实验时间未填（显示录入日期）」灰字提示。
  4. Python 消费方（助手工具/上下文/日报/Word 导出）改用 `experiment_date`，
     Word 导出标签由「记录日期」改为「实验起始时间（来源：时间线/录入）」。
  5. 是否**回写落盘**：建议不改动 `date`（保持「录入日期」原始语义），只在读取层派生；
     若用户希望导出/统计用实验时间，再在 `update_record` 时同步写 `experiment_date`（需确认）。
  6. 测试 `tests/test_records_dates.py`：5 种格式 + 笔误 `2026-8-123` + 空 timeline + 空 process_notes，
     断言 `experiment_date`/`date_source`；再断言列表排序与助手工具输出。
