### 问题 1：深度研究上下文缺失

**原因分析**

1. **现象 1（看不到历史）**：普通对话走 `loop.run(sess, message, …)`，会调
   `build_messages(session, …)`（`src/assistant/loop.py:123`）→ `_history_block(session)`
   （`src/assistant/loop.py:179`）**把历史消息拼进 prompt**；但深度研究走的是
   `research.run_research(question, allow_web, session_id, attachments)`
   （`src/assistant/research.py:576`），**只拿到 `session_id`，全程没有 load_session、没有读历史**——
   `session_id` 只用于「落盘提问/回答」和报告关联（`research.py:604-607、687-697`）。
   计划的生成与报告撰写只带当前 `question` 与检索证据（`research.py:613-614、666-672`）。
   → **深度研究是「无记忆」的独立问答**，与用户感受一致。
2. **现象 2（每问自动生成报告）**：`run_research` 在第 5 步**无条件** `save_report(...)`
   并 `yield {"type":"report"}`（`research.py:681-699`），前端收到后往消息里插一张
   「研究报告《…》」卡片（`webapp/src/pages/Assistant.tsx:426-440`）。
   而「整合整段对话」的报告**另有独立按钮**（`Assistant.tsx:1008-1036` →
   `POST /api/assistant/sessions/{sid}/report` → `research.build_session_report`
   `research.py:823`）。即：**用户想要的那个能力已经存在且是手动触发**，多余的是
   每问一份的「单问报告」自动落盘。

**修复方案**

- 上下文拼接（改 `run_research`）：
  1. 新增 `_conversation_history_block(session, max_chars)`：从 `sessions.load_session(session_id)`
     取 `messages`，取**本会话全部（或最近 N 轮）user/assistant 文本**，按
     「用户：…／助手：…」拼接，超长时**保留最近若干轮**（复用
     `research._conversation_digest`（`research.py:742`）的写法与预算思路，但用于**计划+撰写**而非报告）。
  2. 注入点两处：`plan_steps(question, evidence=…, history=…)` 与撰写 prompt 的
     `研究问题` 段落（`research.py:666-672`）改为「对话背景 + 当前问题」；
     无 `session_id`（独立单问）时保持旧口径，向后兼容既有打桩测试。
  3. 历史预算：默认 6000 字（可用环境变量/参数调），与附件证据并列注入。
- 报告改为用户主动：
  1. `run_research` 增加参数 `save_report: bool = False`（默认不落盘、不发 `report` 事件）；
     仅当显式请求（或前端「深度研究并出报告」勾选）时才保存。
  2. 前端研究模式：去掉「每问自动出报告卡」，改为**完成后只在消息里给一个「生成/更新综合报告」入口**
     （复用现有 `generateSessionReport`，`Assistant.tsx:726`）。
  3. 已有「综合报告」按钮保留为唯一报告生成路径；报告内容已整合全对话
     （`build_session_report` → `_conversation_digest`，`research.py:842`）。
  4. 保留「本次研究结论」作为**普通助手消息**落会话（现在已经是这样，`research.py:692-695`），
     刷新不丢。

**涉及文件**：`src/assistant/research.py`（run_research / plan_steps / _execute_step / 新增 history block）、
`api/routers/assistant.py`（research 端点参数透传）、
`api/schemas.py`（`AssistantResearchRequest` 增 `save_report`/`use_history`）、
`webapp/src/pages/Assistant.tsx`（研究模式去掉自动报告卡 + 报告按钮文案）、
`webapp/src/components/assistant/api.ts`（`researchStream` 参数）、
`tests/test_assistant_research_*.py`（新增历史注入与不落盘断言）。

### 问题 2：文献知识库图谱与补解析

#### 2.1 图谱显示为零 —— **已定位为前端渲染分支 bug（硬 bug，与数据无关）**

**原因分析**（证据链完整）

1. **数据其实存在**：你机器上 `data/literature/figures_index.json` 有 **22 条**记录，
   全部属于 `paper_id=1529`（`spectra 13 / mechanism 8 / structure 1`，`tags=["自动抽取","内嵌图"]`），
   文件在 `data/literature/figures/`（22 个文件）。
2. **接口正常**：安装版实测 `GET /api/literature/figures?paper_id=1529` → **22 张**；
   `GET /api/literature/figures/{fig_id}/file` → **200 image/jpeg**（0.7–2.0 MB）。
3. **UI 却显示 0**：把安装版 UI 驱动到「文献 #1529 → 图谱页签」，实测
   `figTabState=active`、`figImgs=0`、`bodyHasEmptyLib=true`，**截图**显示面板文案为
   「**文献库为空：先在上方「文献录入」入库文献，再为其上传图谱。**」
4. **代码根因**：`LiteratureFiguresPanel` 的渲染分支是
   `loading ? 加载中 : papers.length === 0 ? 「文献库为空…」 : <筛选+上传+画廊>`
   （`webapp/src/components/mine/LiteratureFiguresPanel.tsx:258-266`），
   而该组件在全项目**只被用在「固定文献模式」**（`LiteratureKnowledgeSection.tsx:881-883`
   传 `fixedPaperId`）；固定模式的 `useEffect` 分支
   （`LiteratureFiguresPanel.tsx:139-146`）**只 `setPaperId` + 拉图谱 + `setLoading(false)` 后 return，
   永远不会加载 `papers`** → `papers` 恒为 `[]` → **画廊分支永远不可达**。
   → 这与用户「图谱一直显示为零、无法查看」完全吻合（22 张图一张也渲染不出来）。

**修复方案**

1. 渲染分支修正（最小改动、向后兼容）：
   - 固定模式改为只看 `figures`：`loading ? 载入 : shown.length === 0 ? 「该文献暂无图谱。」 : <画廊>`；
   - `papers.length === 0` 的「文献库为空」分支**只保留给非固定模式**（即
     `!fixedPaperId && papers.length === 0`）。
2. 顺带修：固定模式下不渲染「选择文献」下拉（已做）、不重复请求 `/papers`；
   上传/编辑/删除后 `refreshFigures(paperId)` 已具备（`:244`）。
3. 加回归测试：新增前端组件级测试或（更轻）在后端契约测试旁加 Playwright/自检脚本，
   断言「给定 paper_id 有 N 张图 → 画廊渲染 N 个 `img` 且无空态文案」。
   现成可复用的是 `scripts/ui_screenshot.cjs`（`SHOOT_JS` 探针把 `figImgs` 计入断言）。

#### 2.2 图片查看与标注 —— 需要「文献图片」页签 + 点击放大 + LLM 自动标注

**原因分析**

1. **图片确实已提取并入库**（v1.9.4 起的 `pdf_figures` 抽取 + `figures.add_figure`），
   文件与索引都在；**看不到 = 2.1 的渲染 bug**（画廊整段不可达），
   而不是存储/接口问题。
2. 画廊卡片本身**已有**：类型徽章、图注、标签、下载、**编辑标注**
   （`PATCH /api/literature/figures/{fig_id}`，`api/routers/literature.py:430`；
   前端 `LiteratureFiguresPanel.tsx:376-387`）、删除（`:388-395`）——
   **唯独缺「点击放大」**：`<img>` 没有 onClick，缩略图固定 `max-h-28`（`:324-329`），
   大图（实测 2000×1000+）只能靠「下载原图」看。
3. 页签命名与位置：当前是 `原文信息 / 结构化条目(N) / 图谱`
   （`LiteratureKnowledgeSection.tsx:731-737`），用户期望「原文信息」旁的
   **「文献图片」**页签（语义更直白，且当前 bug 让人以为是"图谱"而不是文献图）。
4. 图注来源：抽取时已用**PDF 文本里的图注**（`pdf_figures.py` 的 `_page_captions`）作为
   `caption`，**无图注的图（SI 里常见）目前是空 caption**（实测 49 页 SI 全部无图注）。
   LLM/视觉自动标注能力**已存在但未接**：`src/literature/vision.py:analyze_image`
   （返回 description/metrics，受设置页「视觉读图」开关控制）。

**修复方案**

1. 页签改造：`图谱` → **`文献图片`**，并移到「原文信息」之后（位置 2），
   页签内计数显示 `文献图片（N）`（N 由 `figures.length` 提供，与 2.1 同修）。
2. 画廊交互：
   - 缩略图 `onClick` → **Lightbox Dialog**：大图（`max-h-[80vh] object-contain`）+
     上一张/下一张 + 键盘 ←/→/Esc + 下载原图 + 当前图注；
   - 卡片保留「编辑标注」（已有）与「删除」（已有），并在 Lightbox 内也能改标注。
3. 标注持久化：复用现有 `PATCH /figures/{fig_id}`（caption/tags/meta/score_note），
   **不需要新表**；标注与文献关联字段是 `paper_id`（`figures.py:167-180` 的 rec 结构）。
4. LLM 自动标注（分级，成本可控）：
   - **一级（默认，零成本）**：入库时把 PDF 图注写进 caption（已实现）；无图注时用
     `caption_label + page` 生成占位（如「Fig. 5（第 7 页，无图注）」），避免空白。
   - **二级（可选，需视觉模型）**：解析完成后对**无图注或用户点选**的图调用
     `vision.analyze_image`，把 `description` 回填 `caption`（并在 `meta` 记
     `caption_source="vision"`、`confidence`），用户可改；设置页沿用现有
     「文献解析 LLM → 视觉读图」开关，关闭时完全不影响一级。
   - 批量上限（如单次 ≤6 张）+ 失败不影响入库。
5. 图片文件端点无需改动（实测 200 正常）；仅补 `mime` 缺失时的兜底（用扩展名推断）。

#### 2.3 补解析后仍显示「暂无摘要」

**原因分析**（实测复现）

1. **实盘证据**：文献 1529 已成功补解析（22 张图即那次产出），但
   `GET /api/literature/papers/1529` → `abstract` 长度 **0**，`authors=[]`、`journal=""`、`year=null`
   → **元数据整批没写进去**。
2. **回填是手动的**：解析响应里的 `paper_meta` 只用于预览，前端有「回填到文献库」按钮
   （`LiteratureKnowledgeSection.tsx:1106`；`backfillMeta` 在 `:390-401` →
   `PATCH /api/literature/papers/{id}`），**解析完成不会自动回填**；用户点了「入库」但没点回填 → 字段一直空。
3. **预览卡片不显示摘要**：预览只渲染 title/authors/journal/doi
   （`LiteratureKnowledgeSection.tsx:1113-1141`），**没有 abstract** → 用户连「LLM 到底提没提到摘要」都看不到。
4. 后端链路本身是通的：`_META_PROMPT` 明确要求 `"abstract": "摘要原文或前 500 字"`
   （`src/literature/llm_extract.py:384`），解析后写入 `meta["abstract"][:2000]`（`:445-447`）；
   回填白名单含 `abstract`（`src/literature/resolver.py:183`），且 `only_empty=True` 只补空不覆盖。
   → **不是 prompt 问题、不是字段不一致，是「没触发写入」+「看不到」**。

**修复方案**

1. **解析后自动回填**（默认开，可在弹窗内取消勾选）：
   解析成功即调用 `PATCH /papers/{id}`（`only_empty=True` 语义不变，绝不覆盖 Crossref 已有值），
   回填 title/authors/journal/year/doi/**abstract**；响应里返回 `updated/skipped` 供 UI 提示
   （沿用现有 `PATCH` 返回结构）。
2. 预览卡片**加摘要区**（两行截断 + 展开），并标注 `abstract` 来源（LLM 提取 / 已存在）；
   同时把「回填到文献库」按钮文案改为「回填缺失字段」并显示将补哪些字段。
3. 文献卡片「原文信息」页签：摘要为空且确实没有时保留引导文案；一旦写入即渲染摘要
   （前端读的就是 `detail.abstract`，无需改）。
4. 兜底：`abstract` 提取为空但已有正文时，用「引言/摘要关键词附近段落」二次抽取
   （`llm_extract.extract_paper_meta` 增加一次带定位提示的重试），仍失败则在预览里
   明确显示「未提取到摘要（可手动粘贴）」，并提供手动填写入口（`PATCH /papers`）。

### 问题 3：科研助手读不到收藏的单体信息（结构式 / CAS）

**原因分析**（逐条带证据）

1. **工具输出被压成一个 label**：`list_favorites` 每条只输出
   `id｜醛/胺 label｜夹名｜分数｜DFT｜记录数｜备注前 80 字`
   （`src/assistant/tools/favorites.py:33-45`），而 label 是
   `name or cas or smiles` **只取第一个非空**（`:28-30`）。你的收藏 name 都是库代号
   （A6/TAPB/TAPT…）→ **CAS 与 SMILES 永不出现**。
2. **`details` 带不上**：`details` 只有 `count/favorite_ids/folders`
   （`tools/favorites.py:88-99`），且 **LLM 只读 `result["text"]`**
   （`src/assistant/loop.py:321、436`），塞 details 无效。
3. **没有单条详情工具**：`registry.py` 17 个工具里收藏相关只有 `list_favorites`（读摘要）+
   `manage_favorite`（仅 add/move/delete，`tools/favorites.py:226-243`）；
   虽然 HTTP 已有 `GET /api/favorites/{fav_id}`（`api/routers/favorites.py:71-76`），
   但助手**不能自调本地 API**（`tools/fetch.py:29-57` 明确拒绝 localhost/内网）。
4. **系统提示只覆盖「当前这一条」**：`context.py:18-67` 会注入 name/cas/smiles，
   但**仅在会话带 `favorite_id` 时**（`:21`），而只有「方案迭代页→转科研助手」才带
   （`webapp/src/pages/Iterate.tsx:160-171`），助手页自建新会话不带（`Assistant.tsx:686`）。
5. **能力连锁**：拿不到 SMILES → `get_monomer_props` 用不上（只吃 smiles，
   `tools/extra.py:13-44`）；拿不到 CAS → `cas_resolve` 方向相反；结构式只能靠
   `GET /api/monomers/structure.svg`（`api/routers/monomers.py:58-80`）现画，助手既无画图工具也读不到本地 URL。
6. **附带发现（真实 bug，建议同批修）**：`tools/extra.py:32-38` 取 facts 的 key 写成
   `molecular_weight/logp/rings`，而 `monomer_props.compute_facts` 实际返回
   `mw/xlogp/aromatic_rings/f_count/…`（`src/recommend/monomer_props.py:52-79`）
   → **助手里「分子量、LogP、芳香环数、氟原子数」永远缺失**（已用 RDKit 实跑比对确认）。
7. 澄清：**CAS/SMILES 在数据模型里是有的**（实盘 `fav_*.json` 含 `"cas": "1300701-03-4"`），
   缺口在**暴露面**（工具输出/详情工具/上下文注入），不在存储面。

**修复方案（"超级入口"原则）**

1. `list_favorites` 逐字段全出：`name / CAS / SMILES（截断显示）/ 角色 / 夹 / 分数 / DFT / 记录数 / 备注(200)`，
   并补 `structure_url`（`/api/monomers/structure.svg?smiles=…`）；注意 `registry._MAX_TEXT=8000`／
   `_MAX_SUMMARY=6000`（v1.9.6 已放宽）。
2. **新增 `get_favorite` 工具**：入参 `favorite_id` 或 `name/cas/smiles`（模糊匹配）→ 返回
   完整单体对象（name/cas/smiles/role）+ notes + latest_prediction + dft_entries 摘要 +
   `properties`（见问题 5）+ references + experiment_record_ids。
3. `manage_favorite` 增 `update` action（改名/CAS/备注/性质），并同步 `manage_favorite_impact`。
4. 修 `extra.py` 的 key 映射（`mw→分子量`、`xlogp→LogP`、`aromatic_rings→芳香环数`、补 `f_count`）。
5. 上下文注入放宽：会话无 `favorite_id` 时，注入「收藏夹概览」（前 N 条：name/CAS/SMILES 摘要），
   让助手在无上下文时也知道你收藏了什么（条数/字数设上限）。
6. 结构式可视：助手消息渲染层把 SMILES / `structure_url` 自动转
   `<img src="/api/monomers/structure.svg?smiles=…">`（前端 `markdown.tsx` 扩展或消息后处理）。

### 问题 4：科研助手支持上传图片与截图

**原因分析**（比预期乐观：链路大半已存在，缺"入口"与"视觉模型归属"）

1. **后端已支持图片附件**：白名单 `.png/.jpg/.jpeg/.webp`（`src/assistant/attachments.py:35`）、
   转 OpenAI vision data URL（`attachments.py:218-225`）、
   `build_user_content` 会拼成 `[{text}, {image_url}]`（`src/assistant/loop.py:85-115`）。
2. **前端已有上传按钮与白名单**：`accept=.png,.jpg,.jpeg,.webp,.txt,.md,.json,.csv,.docx,.pdf`
   （`webapp/src/components/assistant/api.ts:324`）+ 文件选择（`Assistant.tsx:1141-1153`）。
   → 所以「无法上传图片」的准确说法是：**能传，但模型看不懂**（见 3），且**不能粘贴/截图**。
3. **真正的瓶颈是模型能力**：助手用的是助手 LLM（当前 `deepseek-flash`，纯文本）。
   走纯文本端点时 `_plain_content` 会把图片分片替换成
   「[用户上传了图片，当前模型不支持看图…]」（`loop.py:351-371`）→ 用户感觉"不识别"。
   而**视觉配置只存在于文献解析设置**（`vision_enabled/vision_base_url/vision_api_key/vision_model`，
   `src/literature/llm_extract.py:125-156`），助手侧**没有**视觉开关，也不会调用
   `vision.analyze_image`（全仓 grep：只有 literature 用）。
4. **截图/粘贴缺失**：`Assistant.tsx` 无 `onPaste`、无截图入口；
   Electron 侧 `main.cjs` 已有 `ipcMain.handle` 与 `preload.cjs`（contextBridge）
   基础设施（`electron/preload.cjs:29-33`），**加一个截图 IPC 即可**，但需重打 Electron 壳。

**修复方案**

1. 上传体验（前端）：
   - 粘贴：`onPaste` 读 `clipboardData.items` 里的 `image/*` → 走既有上传接口；
   - 拖拽：整块输入区 `onDrop`；
   - 预览：已选图片显示缩略图 + 删除（现有 pendingFiles 区扩展）。
2. 截图（Electron 为主，浏览器降级）：
   - 主进程 `desktopCapturer.getSources({types:['screen','window']})` + 区域选择或
     直接「截取应用窗口」，IPC 通道 `capture-screenshot` → `preload` 暴露
     `window.cof.captureScreenshot()`；前端加「截图」按钮 → 拿到 PNG → 上传为附件；
   - 非 Electron（浏览器调试）用 `navigator.mediaDevices.getDisplayMedia()` 降级。
3. 视觉模型接入（两条路，按是否支持图片输入自动选择）：

1. **收藏模型里没有「性质」字段**：`src/favorites/store.py` 的 fav JSON 字段为

### 问题 6：实验方案卡片内容无用 + 无删除按钮

**原因分析**

1. **方案卡根本不调用 LLM**：`src/recommend/plan_card.py:9` 明确「纯模板 + 结构检测」；
   内容来自**硬编码模板**（`plan_card.py:34-51`、`data/plan_templates/builtin_hou_v3_9.json:5-21`），
   条件全是定性文本（`solvent=甲苯（或氯仿）`、`modulator=苯胺（用量按方案）`、`time_days="2-5"`），
   **数据结构里没有 amounts/dosages/references 字段**（`plan_card.py:193-203`）；
   助手工具 schema 也不给 LLM 写内容的口子（`registry.py:226-240` 只有 smiles/name/template_id）；
   唯一相关 prompt（docx→模板提取）**明令禁止编造数值**（`plan_templates.py:176`）。
   → 对任何单体对都是同一套通用方案，**这就是"毫无用处"的根因**。
2. **用户要的用量其实生成过，但没有通道进卡片**：实盘会话
   `data/assistant/sessions/sess_52426bcadcc0.jsonl`（2026-09-17 18:42）里，助手在聊天中给出了
   「TAPT–A7 氟化 COF 膜合成方案」含精确投料（TAPT 10.6 mg / A7 25.0 mg / 乙酸 0.20 mL /
   苯胺 8.2 μL / 总溶剂 3.0 mL / 三组溶剂对照），而同时落盘的 `plan_20260917_002.json`
   的 conditions 仍是「甲苯（或氯仿）…」；助手自己也点破「卡里条件没有一条来自 A7/TAPT 的历史实验或文献」。
   另一条路径（采纳建议）把用量原文塞进 `adjustments_applied` 而**不改写 conditions**
   （`generated_plans.py:13-15、272-279、290`；实例 `plan_20260821_001.json` 的 `to` 字段里有
   「TFPT 11.8 mg、甲苯 0.6 mL、氯仿 0.4 mL、苯胺 8.2 μL、乙酸 6M 0.20 mL…」）——
   **卡片里一个字都没有**。
3. **三个展示面各丢一半字段**（次因）：
   - `PlanCardPanel.tsx`（打分页/收藏详情）：有 conditions/steps/checklist/hints，**无 aldehyde/amine、无 generated_at**；
   - `PlanCardItem.tsx`（迭代页）：有 steps/checklist/hints/adjustments，**完全不渲染 conditions**；
   - `PlansSection.tsx:251 PlanRow`（我的方案库）：只有 单体/conditions/steps，**丢掉 checklist、monomer_hints
     以及唯一含具体用量的 `adjustments_applied`**。
   字段名本身是对齐的（无渲染不出内容的问题）；空态文案分别是「打分后自动生成方案卡」
   （`PlanCardPanel.tsx:122-126`）、「该方案暂无方案卡内容。」（`PlansSection.tsx:283-284`）、
   「暂无方案：在迭代页采纳建议后…」（`:359-362`）。**另有一个"静默空卡"分支**：
   若模板 `conditions={}, steps=[]`（`validate_template` 只校验类型不校验非空，
   `plan_templates.py:49-71`），`PlanCardPanel` 只渲染「模板：xxx」一行，其余全空。
4. **没有任何删除能力**：`api/routers/iterate.py` 只有 `GET /plans`（`:316`）、
   `POST /adopt`（`:300`）等，**无 `DELETE /plans/{plan_id}`**；
   `api/routers/plan.py:50` 的 DELETE 只删**模板**；前端 `PlanCardItem.tsx`、`PlansSection.tsx`

   其文案还写着「已生成的方案卡不受影响」）；`mine/api.ts` 只有 `deletePlanTemplate`（`:370`）。

**修复方案**

1. **生成逻辑改为"可操作方案"**（核心）：

     catalyst:{name,mL,M}, total_volume_mL, mmol_scale }` 与 `references[]`、`basis[]`（每项来源）；

     `_monomer_obj` `:141-158`），并在卡片上**显式标注依据**（如「按 0.03 mmol 醛基准，

   - 新增「模板 + 覆盖」机制：`generate_plan_card(..., overrides)`，模板提供默认，overrides 落
     `applied_conditions`（新增键，不改原 `conditions`，向后兼容）。
2. **把助手聊天里的方案"落卡"**：给 `generate_plan_card` 工具加可选

3. **删除能力**：
   - 后端 `DELETE /api/iterate/plans/{plan_id}`：`plan_YYYYMMDD_NNN` 正则校验（仿 `iterate.py:286-288`）

     （复刻 `PlansSection.tsx:148-158、226-245` 模式）。
4. **排版与字段统一**：三个面统一为同一字段集（单体对 / 条件 / **用量表** / 步骤 / 核对清单 /
