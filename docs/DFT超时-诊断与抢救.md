# DFT 超时事故：诊断、修复、以及这次计算是怎么被救回来的

> 用户视角：跑了 1 小时的 Psi4 真 DFT 作业被"超时"杀掉，界面提示
> 「Psi4 计算超时（超过 3600 秒仍未完成）」。
> 本文记录：为什么必然超时、怎么修、以及**怎么把已经算完的部分救回来**（没白跑）。

## 一、作业事实（全部有据可查）

| 项 | 值 |
|---|---|
| 作业 | `dft_psi4_1c9a1aadf753_7i0by3gj`（store 里的 job_id `2ca557e9de8747de`）|
| 方法 | ωB97X-D3BJ/def2-SVP（真 DFT），mode=pair，24 线程 |
| 体系 | 复合物 **90 原子** = 片段 A 68 + 片段 B 22 |
| 起止 | 16:41:52 启动 → **17:41:36 被杀**（= 3600s 上限）|
| 目录 | `%APPDATA%\COF-Film-Recommend\data\dft_jobs\dft_psi4_1c9a1aadf753_7i0by3gj\` |

生成脚本里**几何优化是跳过的**（`if False:`），真正的计算是 6 次 SCF：
counterpoise 3 次（E(AB@AB)、E(A@AB)、E(B@AB)）+ 两个单体单点 + 复合物 SCF/wfn。

## 二、诊断：3600s 对这个体系**必然不够**

从被中断那次的 `psi4_output.dat` 里读出的实测进度：

| 阶段 | 累计耗时 |
|---|---|
| CP 第 1 段 SCF | 761s（12.7 分钟）|
| CP 第 2 段 SCF | 1438s（23.9 分钟）|
| CP 第 3 段 SCF + 输出 CP 表 | 2716s（45.3 分钟）|
| 单体 A 单点 | 2732s（45.5 分钟）|
| 单体 B 单点 | 2748s |
| **复合物 SCF（被杀）** | 到 3600s 时已迭代 **第 8 步**，ΔE=1.05e-5、RMS=1.49e-6（判据 1e-6）|

即：**只差 1~2 次迭代**（约 4 分钟）就能收敛，全程约 4000–4500s。
结论：这个体系的合理预算是 1~1.5 小时，3600s 必然超时。

## 三、根因：超时分档自相矛盾

`src/dft/psi4_backend.py::psi4_timeout()`：

```python
if n_atoms is None or n_atoms <= 50: return 1800
if n_atoms <= 90:                    return 3600   # ← 90 原子正好落这里
return 10800
```

而该函数自己的注释写着「>90 原子全档（6 次 SCF）实测约 1.5–2.5 小时，5400s 必超时」——
**90 原子按 ≤90 档给 3600s，与这段实测经验直接矛盾**。
（原子数本来也不是耗时的好代理：基组、元素组成、F 含量、DIIS 行为影响更大。）

## 四、修复

1. **代码**（`psi4_backend.py`）：`>50 原子一律 10800s（3 小时）`，取消 90 这一档；
   ≤50 原子保持 1800s。环境变量 `COF_DFT_TIMEOUT_PSI4` 仍优先（可放宽也可收紧）。
2. **已安装版本立刻可用**（不必等新包）：用户级环境变量
   `COF_DFT_TIMEOUT_PSI4=10800` 已用 `setx` 写入 → **重启 App** 后其后端进程即继承。
3. **测试**：`TestTimeoutTiersV151` 更新为「90 原子 = 10800」并扩充 3 条
   （环境变量放宽到 6h / 非法值退回按原子数 / 空值）。

## 五、把这次计算救回来（不重算已完成的 45 分钟）

被超时杀掉 **≠ 结果全丢**：Psi4 的文本输出里已经落了 5 段**已收敛**的 SCF 能量，
而且它们**算术自洽**（CP 表的交互能正好补上缺口）：

```
E(A@AB) = -1627.4005136562436746      E(B@AB) = -2016.3317125880869298
E(A@AB) + E(B@AB) + E_int = -3643.740000727416
E(AB@AB)                  = -3643.740000727416      ← 差 = 0.000e+00（完全吻合）
E_int   = -0.007774483086 Eh = -4.8786 kcal/mol     ← CP 表直接给出的 BSSE 校正结合能
E(A)    = -2016.3307961364134826      E(B) = -1627.3902854394589212
```

于是只补最后一步（本来只差 1~2 次迭代的那步）：

1. 备份原输出（`psi4_output.timeout-3600s-*.dat`，243,732 字节，证据保全）；
2. 从 `run_psi4.py` **原样解析**原子坐标与片段划分（90 = 68 + 22，不手抄）；
3. 用**完全相同的设置**只跑复合物 SCF + wfn 性质（gap / 偶极矩 / fchk）；
4. **交叉核对**：重算出的复合物能量 `-3643.740002537162` 与上次 CP 块的
   `-3643.740000727416` 相差 **1.81e-6 Eh = 0.0011 kcal/mol**（SCF 判据本身就是 1e-6，
   这点差异比 DFT 自身误差小两个数量级）；
5. 写出 `result.json`：能量口径统一取被中断那次（保证与 CP/单体同源自洽），
   只把 wfn 性质取本次重算，并在 `recovery` 字段里**如实标注**哪些是重算、哪些是沿用。

> 小插曲（如实记录）：第一次跑收尾时我把交叉核对阈值设成 1e-6，结果 1.81e-6 被判为
> "不一致" → 脚本按设计拒绝写结果，白跑 16 分钟。阈值必须按**科学意义**定
> （1e-5 Eh = 0.006 kcal/mol），而不是拍一个看起来严格的数。

## 七、结果怎么回到界面（不改 App 代码）

App 没有"重试/续算"接口，但有**结果缓存**：新建作业时先算缓存 key，命中就直接返回历史结果。
所以落地方式是：用 App 自己的 `compute_pair_binding_psi4()` 组装结果
（只把"真正跑 Psi4"那一步换成读已算完的 `result.json`），再按 `jobs._run_job` 完全相同的方式
算 key 并 `save_cache`：

- 缓存文件：`%APPDATA%\COF-Film-Recommend\data\dft_cache\3dd35e32446f32d73e62fee991079774c7d99fb6.json`
- fchk 归档：`%APPDATA%\COF-Film-Recommend\data\dft_artifacts\4ca71a82d3ac.fchk`
- **key 已用 App 自己的 `probe_cache_key` 交叉验证一致** → 你在界面用**同样的分子/后端/档位**
  再点一次「开始计算」，会**立即**返回这份结果（提示"命中缓存，直接返回历史结果"）。

> 为什么不用"重新跑一遍"来交结果：完整重跑要约 70 分钟且要占满 24 线程；
> 复用已完成阶段 + 只补最后一步只要约 15 分钟，且结果经过交叉核对。

## 八、教训

1. **超时默认值必须用真实作业标定**：档位边界（90 原子）与实际耗时脱节，用户就撞墙。
2. **原子数不是耗时的好代理**：同一档位里不同体系可能差几倍；宁可给宽一点 + 让用户能收紧。
3. **被超时杀掉 ≠ 全丢**：Psi4 输出里有已收敛的能量；先做算术自洽核对，能救则救。
4. **阈值要有科学依据**：1e-6 vs 判据 1e-6 就是过严，白跑一次。
5. 环境坑（本次实测）：**xTB 在当前 shell 下无法在 `%TEMP%` 写入**（`forrtl: severe (256)
   ... file CONOUT$`，崩在 `restart.f90` 写 `xtbrestart`），因此用 pytest 默认临时目录的
   DFT 真跑用例会失败；把临时目录放进仓库内即可全绿：
   `pytest tests --basetemp=.tmp_xtb\pytest-tmp`。已用 `git stash` 证明与本次改动无关。
